# 同一需求的定位、批准与状态

## 定位

- 使用已确认的产品 workspace 和项目指定的需求根目录。默认从 `<workspace>/pmspec/changes/<需求名>/proposal.md` 定位，正式原型默认在同一需求下的 `prototypes/`。
- 新需求默认用 kebab-case。已有需求沿用真实目录名，包括项目认可的版本前缀、大小写和命名格式。名称须为单一目录名，排除绝对路径、分隔符、`.` 和 `..`。用户提供路径时可据此定位。写入前核对解析后的真实目标仍在获授权的需求根目录内。
- 先读项目约定、当前提案和本次涉及的既有资产，检查未提交改动。只有无法唯一定位时才问。整理或原型修订沿用已确认的正式入口；多个版本并存时按批准记录或项目索引选定，修改时间和文件名序号不能代替批准。

## 批准

| 情况 | 执行依据 |
|---|---|
| 写提案 | 已确认的目标、范围和关键规则。可直接进入 Propose |
| 做原型或改行为 | 以现有提案为底稿。用户明确批准提案，或指定版本并要求据此制作，即可开工。修订已有原型时沿用已批准基线，接收用户明确给出的本次变更 |
| 整理已有资产 | 去重、去过程叙述，按已确认口径对齐；涉及业务取舍、增加流程或改行为时，先按明确请求选择相应阶段 |
| 跨会话 | 读取用户指定的批准证据，核对提案版本和变更范围。无法核实时只问会影响本次工作的缺口 |

提案编写完成后等待用户审阅；用户可直接指定下一阶段。文件存在、原型审核通过、Git 合入和产品上线状态各自独立。关键决策缺失时暂停依赖该决策的改动，继续已确定的工作。已经明确的授权不用再确认。

## 需求元数据

YAML Front Matter 放在 `proposal.md` 文件首行。示例：

```yaml
---
name: simplify-project-creation
version: "1.14.1"
status: 未评审
---
```

- `name` 与实际需求目录名一致。`version` 是已确认的产品发布版本，使用带引号的字符串保留原格式；从用户说明或明确的发布安排获取。新建缺版本先问，存量缺字段不猜，独立于该字段的整理可继续。
- `status` 支持 `未评审 / 待发布 / 已发布`。新建默认未评审；后两项表示产品功能待上线和已上线。修订默认保留版本和状态。只有用户明确指出目标需求和状态时才更新，已发布内容的文案或事实修正保留原状态。若用户提出尚未上线的行为，先核对该变化归属原需求还是新迭代，不把新行为记成已上线。
- 正文、原型和索引引用提案的元数据。获准迁移旧格式时保留正文、已确认版本及状态。只要求更新状态时，只改现有状态值；缺少可定位的状态字段时说明缺口。
