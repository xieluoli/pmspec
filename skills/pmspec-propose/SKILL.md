# PMSpec · Propose

把已批准的需求整理成可独立阅读的正式提案。全程中文。输入为 `$ARGUMENTS` 中的需求名，以及当前对话或用户指定的获批准需求来源。不要求先运行 explore。

## 输入与定位

1. 确认当前项目 workspace；路径不明确时先询问，不自行选其他项目或写入用户主仓。
2. 名称使用简短 kebab-case，只允许小写英文、数字与单个连字符分隔，如 `simplify-checkout`。不允许绝对路径、斜杠、`..`；版本需求沿用项目命名约定时也须保证目录名安全。
3. 未传名称时推荐一个名称；只有名称、没有具体需求时不能猜内容。关键产品决策不明确则一次只问一个问题，不能靠写稿替代确认。
4. 遵从项目指定的需求根目录；无约定时目标为 `<workspace>/pmspec/changes/<需求名>/proposal.md`，后续 Apply 沿用同一目录。先读取已有目录、proposal 及相关资料；已有同名需求时续写最终口径，不直接覆盖他人内容。若名称碰撞或同时有未确认改动，先协调。

## 产出边界

- 只创建或修订上述 proposal。新建时使用本技能自带的 [模板](templates/proposal.md)，填写实际内容并移除说明注释。
- 不生成 spec.md、design.md、tasks.md、独立 PRD 或额外决策记录；不调用 OpenSpec、其他技能或外部 CLI。
- 只写已批准范围，不静默增删模块，不替研发选实现，不自动提交、推送、归档。

## 文档规则

| 章节 | 要求 |
|---|---|
| Why | 陈述有依据的产品现状、问题与本次目标，简洁直接。明确区分已上线现状与其他版本计划。 |
| What Changes | 按功能模块说明新增、调整或移除的行为，保留影响行为的关键权限、触发条件、默认值、限制和异常结果。 |
| Capabilities | 分 New Capabilities / Modified Capabilities 列产品能力及简短说明。能力名称描述持续的产品行为，不是本次施工动作；复用已知名称，没有能力清单就如实说明未核对。无相关项写“无”，不虚构。这里只是产品能力索引，不承诺生成 specs/。 |
| Impact | 写受影响的用户、功能或平台，必要依赖、兼容影响及产品风险。不列逐文件改动、研发分工、无依据工期或版本路线清单。 |
| 范围边界（按需） | 有易混淆边界时，明确本次不做什么。 |
| 验收要点（按需） | 有成功标准需要落文时记录可判断的产品结果，不展开测试脚本。 |

### 写最终需求，不写聊天记录

- 禁止“根据本轮讨论”“用户后来要求”“原方案撤销”等过程叙述、辩护或补丁堆叠。
- 修订未上线需求时直接整理成完整最终口径，不把旧草案包装成生产事实。
- “由 A 调整为 B”仅在 A 是有依据的真实产品基线时使用；A 不能只是聊天中的旧想法。
- 背景来源限用户明确提供的事实、可核对的已生产内容或其他版本需求；后者标清计划属性。影响判断的依据尽量用可访问链接或文档相对路径指明，不另建来源正文副本。

### 简洁不等于丢规则

- 每模块优先一条主 bullet，必要时少量子项；不机械限制字数，不写“优化体验”等空话。
- 不写像素、颜色、圆角、组件或路由名等视觉与实现细节。属于产品决策的文案、数值、状态及兼容性要求必须保留。
- 决定需求含义的规则不能推迟到尚不存在的 spec。页面级细节后续由原型旁注承载。
- 同一规则维护一处，其他位置必要时引用；不能靠重复堆叠显得完整。
- 阻碍立项的未知先澄清。非阻塞假设放在相关章节，明确假设及其影响；不写成确定事实。

## 内置交付检查

写完不直接交付初稿，逐项检查并修订：

1. 与获批准范围逐项核对，有无漏项、擅自扩项、冲突或把假设写成事实。
2. 四个核心章节齐全，能力名称与事实依据可靠；按需章节有必要才保留。
3. 清除对话演变史、视觉量纲与研发实施内容；关键产品规则不因瘦身丢失。
4. 不读聊天记录的人也能理解本次为什么做、做什么、影响什么。
5. 核对文件已写入，已有非本次改动被保留，未生成额外工件。

交付说明相对路径、实际变更和未决项，等待用户审阅。文件生成不代表提案获批。用户明确确认后，给出含实际名称的 `/pmspec-apply 需求名`，Codex 改用 `$pmspec-apply 需求名`，不自动调用。跨会话时须有明确批准依据，不能仅因文件存在而视为批准。
