# 两文件交付与过程材料清理

正式需求默认只留 `proposal.md` 和 `prototypes/<入口名>.html`；无需原型的 Propose 阶段只交 proposal。新增页面继续在同一 HTML 向下平铺。拆分 HTML 或增加附件须用户明确批准，不能因文件曾存在或被引用就视为获准交付。

“两文件”仅约束单次需求目录，不约束 Init 经确认建立的项目级 `pmspec/design/`：`DESIGN.md`、通用规范、组件、页面模式与品牌资产均不在该清理范围内。清理不撤销设计依据的来源版本、采用状态及本次批准范围，也不代替设计初始化的人工确认。

## 制作与审核期间

- **旧稿保护不等于永久交付**：开工先核对已有文件、他人改动与批准范围，不覆盖或删除未知内容；需保留的工作副本放在需求目录外的运行临时区，不在需求内建立 archive/。
- 截图、测试脚本/结果、交审说明、审核报告、旧 HTML 和来源摘录从生成起放在需求目录外的运行临时区，不进入研发导航、提交清单或发布包。临时区遵从宿主的工作区约束，不写共享目录或用户主目录；不新增强制配置或依赖。
- 主 Agent 把临时证据的实际位置、HTML 版本、设计来源及批准范围交给命名审核 Agent。审核者仍须读取当前证据；缺证据不能通过，不因减少交付文件而取消浏览器实测、独立审核或复审。
- 审核未完成、待裁决或仍需复审时保留所需证据，不提前销毁。临时文件存在不等于永久可达，不把运行本机路径交给读者当交付链接。

## 交付前清理卡点

1. **盘点并确认授权**：列出需求目录全部文件、用途、归属、引用和拟保留/移除项，核对 Git 与未提交改动。用户批准的是具体清理范围；没有删除授权，或遇到他人文件、来源不明内容、未确认改动时，暂停受影响删除并请用户确认，其余工作继续。禁止按扩展名、通配符或递归删除整个目录。
2. **先迁移有效信息**：必要业务规则合入 proposal 或对应原型旁注，不丢权限、边界和待确认契约；素材内嵌到 HTML。来源使用共享规范或固定版本的可达引用，不复制正文充数。保留项目级 DESIGN 与共享设计资产，不把“两文件”扩成全仓清理。
3. **留痕后移除**：完成当前版本的浏览器实测、命名独立审核及必要复审后，将版本标识、审核结论、验证范围、Not run 与必要证据存入宿主持久任务记录或经批准的外部记录，再按已确认清单移除多余材料。不用需求目录内归档代替清理；Git 可追溯的旧稿引用固定提交，不恢复到研发阅读目录。若没有可用留痕渠道，保留需求目录外的证据并报告阻塞，不声称清理闭环完成。
4. **修复引用并复核**：更新 proposal、README 和共享设计入口中受影响的链接/锚点，研发主路径只指向正式产物。静态核对最终文件清单、自包含资源和全部受影响引用；移除文件后补测关键入口、返回和资源加载。HTML 字节未变且既有证据适用时可引用原审核，不冒称新审；HTML 有改动则更新版本、补测并交命名 Agent 复审。
5. **交付后处置**：确认任务记录中的证据已可访问，再清理本次自建的临时副本；不触碰其他运行的文件。缺少持久记录时暂留并说明，不把清理失败藏在“审核通过”里。

交付前核对需求目录恰好两文件（Propose 阶段一文件），或与用户明确批准的额外清单逐一相符。另说明浏览器实测、独立审核、人工验收分别处于什么状态；整理文件不等于提交、推送、合入或同步安装/平台镜像，这些动作仍各需授权。
