# 正式交付、历史稿与过程证据

正式入口默认两件，`proposal.md` 与 `prototypes/<入口名>.html`。Propose 只交提案。新增画面进入同一个 HTML；拆分原型或将附件纳入正式交付须用户明确批准。项目级 `pmspec/design/` 和其他既有资产的归属按项目约定。

## 当前稿与历史稿

- 写入前检查正式入口、已有文件与未提交改动。未审阅草稿可在本次授权范围内续写；新方案或已审阅版本的改版使用不冲突的新文件名。默认把 HTML 候选放在需求的 `prototypes/`，交付时标明候选和当前正式入口。候选与正式稿对应不同提案修订时，给出各自对应的固定提交或快照。
- 用户确认候选替换正式入口后，更新获准修改的索引与链接。明确要求继续使用原文件路径时，先保留可恢复的旧版本，再更新原路径。历史稿有 Git 记录时用固定 commit 追溯，未纳入 Git 的已审阅版本应保留原件或移至用户认可的存放位置。
- 交付清单说明当前应读的文件。目录内因保留历史、等待授权或存在其他用途的文件，可以并存；这类文件本身不计入原型审核缺陷。若它们造成入口歧义、断链或额外运行依赖，按实际影响审核。

## 验证与清理

1. 截图、测试和交审材料放在需求目录外。审核、复审和待裁决期间保留当前 HTML 版本、实际证据与报告。完成审核后，将后续需要的证据存入可访问的任务记录或批准位置；无法持久留存时暂留并说明。
2. 仅清理本次自建临时材料或获准删除的具体文件。先检查用途、归属、引用和未提交改动，保留他人内容、未确认的历史和项目级设计资产。必要规则合入提案或旁注，必需素材内嵌，修复获准范围内的引用后再移除。无删除授权时保留文件并继续交付；证据留存和原型审核分别核对。
3. 清理后检查入口与资源可达。HTML 字节或相关依赖发生变化时补测并按审核契约处理；仅清理无关文件时可引用仍适用的原版本证据。汇报正式或候选入口、浏览器实测结果、独立审核状态与待人工验收项。额外的归档、提交、推送或部署按用户指令执行。
