# Prototype Review · 审核清单

只读审核原型质量和对已批准提案的忠实度。不承担尚未启用的需求逻辑预审，不替用户验收。

## 1. 覆盖与一致性

- 逐项对照 proposal 的模块、关键规则与范围；说明未覆盖项，不能默认为无需展示。
- 读取 [项目设计依据与审核交接](design-context.md)，与生成端使用同一来源、版本及批准范围；无项目依据可用内置默认主题，不要求先建 DESIGN。不按版本号或修改时间认定正式版本，不把本需求采用草稿误判为必须先获全局批准。
- 通用区域与基准一致，没有无关改动；有意偏离有用户批准依据。
- 页面交互、旁注、proposal 三者无冲突；示例数据与模拟结果明确，不泄露真实敏感资料。

## 2. 结构与展示完整性

- 全文件唯一索引，全部独立图示可定位，ID/编号/锚点一致。
- 每个图示恰好一个外壳与一份功能概览。
- 新页面、弹窗、抽屉、不同流程步骤独立平铺，初始即可看到。点击演示不能代替独立图示。
- 轻量状态才可子 Tab；关键结构/流程/决策差异不藏在 Tab。评审 Tab 与产品真实功能区分，旁注覆盖各状态。
- 叠加态有正确底层上下文，平铺图中的弹窗默认可见；关闭/返回路径清楚。
- ASCII 结构图、文字规则及实际 HTML 一致；设备支持如实说明。

## 3. 可用性与自包含

- 关键入口、按钮、字段、校验、失败恢复与返回有实际行为；控制台无相关错误。
- 每屏作用域隔离，无重复 ID、多次监听或跨屏串数据；快照与联动语义明确。
- 三个内嵌标记已回填，CSS/JS/必要图片字体无网络和本机文件依赖。
- 依据浏览器实测证据检查溢出、遮挡、滚动、主要控件可见性。源码检查不能替代实测；证据不足列 Not run。
- 按来源映射分别核对组件变体复用、页面骨架及受影响关键控件的最终生效样式；不能只看色值。保留批准范围外的布局与操作，产品样式不被评审层或后置 CSS 覆盖。自包含 HTML 可保真映射，合理新增组件不因新类名就判缺陷。
- 浏览器证据有当前文件版本标识；改动后更新受影响项，不能复用旧结论。不规定固定断言数量或全量样式矩阵；真实 APP/后端未运行不自动阻塞纯原型审核。

## 4. 旁注与维护边界

- “功能概览”按视觉顺序、加粗元素名前缀、产品语言，内容与当前画面及子 Tab 一致。
- 关键条件、权限、默认值、异常、恢复有落点；无聊天变更史、技术实现、视觉量纲或失效待决项。
- 改版仅讲本次差异，内容级引用可定位，不跨图混写。
- 共享规范/组件沉淀只提建议，不擅自修改。

## 5. 百分制评分（唯一评分表）

设计依据沿用 [设计交接](design-context.md) 的来源顺序与本次批准范围；无项目设计系统时用内置主题和组件评分，不强制先建 DESIGN。下表同时供两种宿主使用，不在 Agent 定义中复制权重。

| 检查项 | 维度 | 满分 | 可核验标准 |
|---|---|---:|---|
| C1 | 组件复用与变体 | 10 | 关键组件有来源与原型位置映射；已有组件保真复用，合理新增有需求依据 |
| C2 | 组件复用与变体 | 10 | 按钮、弹窗、关闭控件等的尺寸、结构、图标与变体符合设计依据 |
| C3 | 组件复用与变体 | 10 | 组件的默认、禁用、加载、错误等适用状态一致，无跨屏样式污染 |
| L1 | 页面骨架与布局 | 10 | 导航、区域顺序、页面模板与设计依据及批准范围一致 |
| L2 | 页面骨架与布局 | 10 | 无关布局、入口顺序和既有操作保留；改动有批准依据 |
| V1 | 视觉规范 | 5 | 字体、字级、颜色及图标符合本次设计依据 |
| V2 | 视觉规范 | 5 | 间距、圆角、边框及阴影符合本次设计依据 |
| V3 | 视觉规范 | 5 | 受影响关键控件有最终生效样式证据，无默认或后置规则意外覆盖 |
| R1 | 需求与范围一致性 | 5 | proposal 的模块和关键规则逐项覆盖，遗漏有明确说明与依据 |
| R2 | 需求与范围一致性 | 5 | 权限、默认值、状态边界与已批准需求一致，无越界改版 |
| R3 | 需求与范围一致性 | 5 | 画面、交互、旁注无冲突，模拟与示例数据明确且非敏感 |
| E1 | 交互与运行证据 | 5 | 当前版本的关键流程、校验、失败恢复及返回已实测，结果可核对 |
| E2 | 交互与运行证据 | 5 | 自包含、控制台、溢出与遮挡检查有当前证据；无必需资源外部依赖 |
| A1 | 平铺展示与旁注 | 5 | 独立页面与叠加态完整平铺，唯一索引、一图一壳一旁注，子 Tab 仅含轻量状态 |
| A2 | 平铺展示与旁注 | 5 | 旁注遵循视觉顺序和产品语言，覆盖当前画面、状态及必要恢复路径 |

六维满分依次为 **30 / 20 / 15 / 15 / 10 / 10**，合计 100。

- 每个检查项只取满分或 0 分，不凭印象酌扣：全部适用检查有证据且符合依据则满分，存在明确偏差则 0 分。多处同类偏差不重复扣同一项；同一问题确实影响多个检查项时分别说明证据。
- 未验证或证据不足的检查项暂计 0 分，写明缺什么；不等于已经证实实现错误。没有某种状态/页面时，核实需求确实不适用并给依据后按已验证计分，不随意删除检查项或重算分母。
- 每项列出规范条目、原型定位与证据；扣分必须可追溯。可选改进建议不扣分，未采纳也不扣分。必改项与一般偏差分别标识，不能把必改降为建议来凑分。
- **通过条件同时满足**：总分至少 90；未解决必改项为 0；影响判断的待确认项为 0；必需证据齐全；没有未验证检查项。高分不能抵消硬性缺陷。
- 复审重新核查上一轮问题与受影响项，按当前版本输出完整评分，不能只回“已修复”或沿用旧分数。

## 输出

先列目标与版本标识、实际读取的需求/设计依据、适用批准范围、套件审核定义与清单、浏览器证据覆盖范围。按“明确缺陷 / 待确认问题 / 改进建议 / Not run”批量输出；每个问题给文件:行号或 section ID、规范条目、证据、影响、建议及关联检查项。必改项标识清楚，无问题写“无”。

评分区必须包含上表全部 15 个检查项，各占一行，顺序与表头如下。得分使用整数，状态仅取“已验证 / 缺陷 / 未验证”；证据列不得空。已验证为满分，缺陷或未验证为 0 分。随后列六维小计与总分（只相加，不另行扣分），每行使用“维度名：整数”，最后使用“总分：整数”，不加列表符号。

```text
| 检查项 | 得分 | 状态 | 依据、定位与证据 |
|---|---:|---|---|
| C1 | 10 | 已验证 | 设计条目、原型位置、证据位置 |
（其余检查项逐行填写，不能用省略号代替）
```

结论前另列三行供主 Agent 校验，数量与上文未解决问题一致；“待确认项”仅统计影响范围、权限、验收或评分判断的问题：

```text
必改项：0
待确认项：0
必需证据：齐全
```

末行严格为 `审核通过 N分` 或 `审核不通过 N分`，N 为 0–100 整数且与分项合计一致；无加粗、代码围栏、句号或后续文字。不再使用“可交付 / 需修订 / 审核阻塞”作为末行。通过也仅表示本轮独立审核通过，不等于人工验收。

缺资料或必需验证时，列 Not run、相关项暂计 0 分并以“审核不通过 N分”收尾。若审核定义/清单本身无法读取，无法可靠评分，直接报告审核未完成与阻塞，不编分数；主 Agent 应将其视为无有效审核报告。初始化的规则读取冒烟也不评分、不输出原型结论。
