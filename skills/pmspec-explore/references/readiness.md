# 需求就绪判定

供澄清、提案等阶段引用。判断的是能否写出没有关键歧义的产品需求，不是技术细节是否穷尽；不得用 Agent 假设填平产品决策。

## 何时检查

每次用户答复澄清、补充条件或改变已确认规则后，重新检查受影响的流程和场景。优先查获授权资料与既有规范，只追问仍会实质改变目标、范围、权限或验收的缺口。

## 六项标准

| 维度 | 达标条件 |
|---|---|
| 目标与事实 | 问题、目标用户、核心场景和成功标准可判断；已上线事实、历史计划、用户决策及待验证假设有区分。 |
| 范围与入口 | 本次做与不做、入口及操作对象明确；多个入口的作用范围、原有入口/能力保留或替代关系无歧义。 |
| 主流程闭环 | 从进入、默认状态、关键操作到结果及退出有完整路径；需要的前置条件与后续动作明确，不出现有入口无结果、有结果无去向。 |
| 角色与权限 | 涉及的登录态、角色/权益、限制时机、允许与拦截结果明确；被拦截后的返回或再次操作路径明确，不存在免费/付费或新旧路径绕过冲突。 |
| 状态与恢复 | 按实际业务覆盖正常/无须处理、进行中、成功、失败/部分成功、中断/取消、重试/重新进入等适用分支；关键状态下允许的操作与恢复结果明确。不适用分支可排除，但不默认为已覆盖。 |
| 验收与验证缺口 | 关键规则有可观察的验收结果；如要求埋点，触发时机、入口归因、结果粒度及拦截/取消与失败的区分明确；影响立项的验证缺口已解决，非阻塞未知有明确影响且不被写成事实。 |

## 如何判定

- **阻塞缺口**：不同答案会改变目标、功能范围、操作对象、权限边界、主流程或成功/失败验收；必须继续澄清，不能靠写提案或原型替用户作决定。
- **非阻塞未知**：可依既有规范处理、可逆且不改变已批准范围的呈现或实现细节；按规范处理并简述依据，或标明待验证内容及影响，不为此反复求批。
- **可以收敛**：六项均已明确、可由授权资料确定或确实不适用，且没有阻塞缺口；给共识摘要供用户确认。
- **可以提示 proposal**：达到“可以收敛”且共识获用户明确确认。给当前宿主可用、带实际需求名的完整提案命令；只提示，不自动执行。

## 对用户怎么说

自行完成检查，不机械输出整张检查表。尚有缺口时简述影响，一次只问最上游、最关键的一题；没有缺口就收敛，不穷举假想场景。普通澄清答复后自然继续，不要求重复输入澄清技能命令，也不在每次回复反复声明当前技能名。新信息推翻已批准规则时，只重新确认受影响部分。
